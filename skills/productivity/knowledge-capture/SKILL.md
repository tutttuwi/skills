# Knowledge Capture

この会話で得た学びを `knowledge/yyyy-mm-dd_<概要>.md` として登録する。過去のナレッジに関連するものがあれば、Obsidian のリンク (`[[...]]`) で結ぶ。

登録先は二種類。

- **リポジトリ** (GitHub / GitLab): ブランチを切って push し、PR / MR を作る。デフォルトブランチへは直接書き込まない。
- **ローカルディレクトリ**: 指定した作業ディレクトリの `knowledge/` にファイルを書く。git 操作はしない。

ファイル形式とリンクの規則は [FORMAT.md](./FORMAT.md)、登録先ごとの具体的な手順は [DESTINATIONS.md](./DESTINATIONS.md) にある。

引数は `/knowledge-capture [登録先] [残したい内容のメモ]`。どちらも省略できる。

## 手順

### 1. 学びを抽出する

会話を振り返り、あとで再利用できる学びを洗い出す。ユーザーが内容を指定していれば、それを優先する。

残す価値があるもの:

- 原因と解決策 (エラー、ハマりどころ、回避策)
- 選択肢の比較と、その結論に至った理由
- 動いたコマンド、設定、コードの断片
- 次に同じ状況になったとき効く判断基準

残さないもの:

- その場限りの作業ログや、結論のない試行錯誤
- 秘密情報 (トークン、パスワード、鍵、内部 URL の認証情報)
- 個人情報、顧客情報、社外に出せない内部情報

一回の会話に複数のテーマがあるときは、一テーマ一ファイルに分ける。分けるかどうかは候補を見せてユーザーに決めてもらう。

### 2. 登録先を決める

次の順で決める。

1. 引数で指定された登録先 (リポジトリ URL、`owner/repo`、ローカルパス、または設定済みの登録先名)。
2. `~/.config/knowledge-capture/config.json` の `default`。
3. どちらもなければ、ユーザーに聞く。

聞くときは「GitHub / GitLab リポジトリか、ローカルディレクトリか」と具体的な場所を尋ねる。答えをもらったら、次回から省けるよう設定ファイルに保存するか尋ねる。設定ファイルの形式は [DESTINATIONS.md](./DESTINATIONS.md)。

リポジトリが公開かどうかを確認し、公開リポジトリには社内情報を含めない。

### 3. 既存のナレッジを調べる

登録先の `knowledge/` を調べる (リポジトリは [DESTINATIONS.md](./DESTINATIONS.md) の手順で先に取得する)。

- 一覧とタイトル、タグを見て、今回の学びと主題が重なるファイルを探す。
- 手がかりになるキーワード (技術名、エラー文、ツール名) で `grep` する。
- 候補は frontmatter と要約を読んで、本当に関連するかを判断する。ファイル名の字面が似ているだけのものは外す。
- ほぼ同じ内容のナレッジがすでにあれば、新規作成ではなく既存ファイルへの追記を提案する。

`knowledge/` がまだなければ、新規作成する前提で進める。

### 4. ドラフトを作る

[FORMAT.md](./FORMAT.md) に従って書く。

- ファイル名は `yyyy-mm-dd_<概要>.md`。日付は今日。
- 関連する過去のナレッジは `## 関連` に `[[ファイル名]]` で並べ、一言で関連の理由を添える。
- 会話ログを貼り写さず、読み手が単独で理解できる形にまとめる。
- 秘密情報や個人情報が混ざっていないか、書き終えたあとにもう一度見直す。

### 5. ユーザーに確認する

書き込みや push をする前に、次を見せて承認を得る。

- 登録先 (リポジトリなら、どのリポジトリ・どのベースブランチに PR / MR を出すか)
- ファイル名とドラフト全文
- 関連リンクとして選んだ過去のナレッジ
- 修正を依頼されたら直して、もう一度見せる

承認を得るまでは、ファイルの作成も clone 以降の git 操作もしない。ただし登録先の調査 (clone、一覧、grep) は読み取りだけなので承認前にやってよい。

### 6. 登録する

- ローカルディレクトリ: `knowledge/` を必要なら作り、ファイルを書く。
- リポジトリ: ブランチを切り、ファイルだけをコミットして push し、PR / MR を作る。手順は [DESTINATIONS.md](./DESTINATIONS.md)。

過去のナレッジへの逆リンク (過去ファイル側からの参照) は、既存ファイルを変更するので、ユーザーが望んだときだけ追記する。

### 7. 結果を報告する

登録したファイルのパスと、リポジトリなら PR / MR の URL を伝える。関連リンクを貼った過去ナレッジも添える。push や PR 作成に失敗した場合は、どこまで済んだかと、ユーザーが取れる次の手を書く。

## 守ること

- デフォルトブランチへの直接 push、force push、既存ブランチの上書きをしない。
- 既存のナレッジファイルを黙って書き換えない。
- 一つの登録で触るのは新規ナレッジ一ファイルだけ (追記を承認された場合を除く)。
- 認証が通らないときは、資格情報を探し回らず、ユーザーにログインを頼む (`! gh auth login` など)。
