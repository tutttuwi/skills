# Output From Know

`put-know` で貯めたナレッジを材料に、記事を書いて出力する。出力先は、指定したリポジトリ (GitHub / GitLab) の指定したディレクトリか、ローカルのディレクトリ。リポジトリの場合は PR / MR で出す。

引数は `/output-from-know [テーマ] [--to <出力先>]`。

- テーマ: 記事にしたい話題、キーワード、またはナレッジのファイル名。省略したら聞く。
- 出力先: 出力先名、`owner/repo:ディレクトリ`、URL、ローカルパスのどれか。省略したら設定ファイルの既定を使う。

記事の書き方の指針は [ARTICLE.md](./ARTICLE.md)。

## 手順

### 1. 材料のナレッジを集める

Skill ツールで "know-setup" を呼び、「ナレッジの保存先を解決する」(節 A、用途はナレッジ) を実行する。次に Skill ツールで "get-know" を呼び、テーマの検索語でナレッジを探す。

- ファイル名で指定されたナレッジは、検索せずにそのまま読む。
- 候補は、frontmatter、`要約`、`学び`、`関連` まで全文を読む。`関連` のリンク先も、話がつながるものは読む。
- 材料にするナレッジの一覧 (タイトル、日付) をユーザーに見せ、足す・外すを決めてもらう。材料が一件もなければ、そこで止めて、`/put-know` でナレッジを貯めるよう促す。

### 2. 出力先を決める

Skill ツールで "know-setup" を呼び、「保存先を解決する」(節 A、用途は出力先) を実行する。`--to` の指定があれば渡す。

- 出力先が未設定なら、`know-setup` がユーザーに聞いて設定ファイルに登録する。ディレクトリ (例 `content/posts`) は必ず聞く。
- 出力先がリポジトリなら、返ってきた読み取り用の clone を使って、既存の記事を調べる (手順 3)。

**公開範囲を確かめる。** 出力先が public で、材料のナレッジが private なリポジトリやローカルにあるときは、ナレッジにある内部情報が記事に漏れる恐れがある。その場合は、ユーザーに公開してよい範囲を確認し、手順 4 で内部情報 (社名、社内 URL、顧客名、非公開のリポジトリ名など) を除く。

### 3. 出力先の既存記事に合わせる

出力先ディレクトリにある既存の記事を、新しい順に三件ほど読み、次を揃える。

- ファイル名の付け方 (日付つきか、スラグか、ディレクトリ分けか)
- frontmatter の項目と書き方 (title、date、tags、公開フラグなど)。Zenn、Qiita、Hugo、Jekyll など、そのリポジトリの流儀に従う。
- 見出しの階層、文体 (です・ます / である)、一記事の長さ
- 画像やコードブロックの扱い

既存の記事がなければ、出力先の設定の `note` に従う。それもなければ、frontmatter に `title`、`date`、`tags` だけを持つ素直な Markdown にし、ファイル名は `yyyy-mm-dd_<スラグ>.md` にする。決められなければ、ユーザーに聞く。

### 4. 記事を書く

[ARTICLE.md](./ARTICLE.md) に従って書く。

- 材料のナレッジに書かれている事実だけを使う。ナレッジにないことを、もっともらしく足さない。足りない部分は、ドラフトの末尾に「要確認」として書き出す。
- ナレッジの Obsidian リンク (`[[...]]`) は、記事には残さない。出典として、PR / MR の本文にだけ書く。
- 秘密情報と個人情報は、書かない。手順 2 で決めた公開範囲に反する内部情報も書かない。

### 5. ユーザーに確認する

書き込みや push をする前に、次を見せて承認を得る。

- 出力先 (リポジトリ、ベースブランチ、ディレクトリ、ファイル名)
- 記事の全文
- 材料にしたナレッジの一覧と、「要確認」の点
- 修正を依頼されたら直して、もう一度見せる

承認を得るまでは、ファイルの作成も、ブランチ作成以降の git 操作もしない。

### 6. 出力する

- **ローカルディレクトリ**: `<path>/<dir>/` に記事のファイルを書く。同名のファイルがあれば、上書きせずに、名前を変えるか確認する。git 管理下でも、コミットや push はしない。
- **リポジトリ**: Skill ツールで "know-setup" を呼び、「変更を PR / MR で公開する」(節 B) を実行する。ブランチ名は `article/yyyy-mm-dd-<スラグ>`、コミットメッセージとタイトルは `docs: add article - <タイトル>`。PR / MR の本文には、記事の概要、材料にしたナレッジの一覧 (ファイル名)、「要確認」の点、レビューしてほしい点を書く。

### 7. 結果を報告する

出力した記事のパスと、リポジトリなら PR / MR の URL を伝える。材料にしたナレッジも添える。失敗したときは、どこまで済んだかと、ユーザーが取れる次の手を書く。

## 守ること

- デフォルトブランチへの直接 push、force push、既存ブランチの上書きをしない。
- 出力先の既存の記事を、黙って書き換えない。一回の出力で触るのは、新規の記事一ファイルだけ。
- 材料のナレッジは変更しない (読み取りだけ)。
