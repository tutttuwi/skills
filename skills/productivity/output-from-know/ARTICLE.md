# ナレッジから記事を書く指針

ナレッジは「自分用の覚え書き」、記事は「知らない読者に向けた文章」。そのままつなぐのではなく、読者の目線に書き直す。

## 読者と主題を決める

- 読者は誰か (同じ問題に当たった人、これから始める人など)。ユーザーが指定していなければ、材料から推測して、ドラフトの冒頭に「想定読者」として一行添える。
- 主題は一つに絞る。複数のナレッジを材料にするときは、一本の筋に沿って並べる。筋に乗らないナレッジは、使わない。
- 材料が薄い (一件で、要約しか書かれていないなど) ときは、無理に長くせず、短い記事にする。

## 構成

出力先の既存記事に型があれば、それに従う。なければ次を基本にする。

1. **導入**: 何の話か、誰に役立つか。二〜三文。
2. **背景・状況**: どういう場面で起きたか。ナレッジの `背景`。
3. **本題**: 原因、解決策、判断の理由。ナレッジの `学び`。手順は番号つきにし、コマンドやコードはコードブロックにする。
4. **まとめ**: 要点を二〜三行。次に取れる手や、注意点。
5. **参考**: 公式ドキュメントや Issue の URL。ナレッジの `参考` にあるもの。

タイトルは、読者が検索しそうな語を入れて、内容が分かるようにする。

## ナレッジから記事への書き換え

| ナレッジ | 記事 |
| --- | --- |
| 「あのときの」「前回の」など、自分の文脈 | 読者が分かる説明に直す |
| 結論だけの箇条書き | 理由と前提をつないだ文章にする |
| `[[ファイル名]]` のリンク | 残さない。必要なら、リンク先の要点を本文に書く |
| 日付 | 記事の日付 (出力する日) にする。出来事の日付が重要なら、本文に書く |
| `tags` | 出力先の既存記事のタグに揃える |

## 事実に忠実であること

- ナレッジに書かれていることだけを、事実として書く。バージョン、数値、コマンドは、ナレッジのまま写す。
- ナレッジが古い可能性がある (日付が古い、ツールが更新されやすい) ときは、「執筆時点の情報」であることを記事に書き、PR / MR の本文でも指摘する。
- 補足したいことがあれば、本文に混ぜず、ドラフトの末尾に「要確認」として分けて書く。ユーザーが確認してから、本文に入れる。

## 出す前の確認

- 秘密情報 (トークン、鍵、内部 URL の認証情報) がない。
- 個人情報、顧客名、社内のサービス名・リポジトリ名など、公開範囲に合わない情報がない。
- 材料のナレッジにない主張が、本文に混ざっていない。
- コードブロックのコマンドが、ナレッジにあったものと一致している。
